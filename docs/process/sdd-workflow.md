# SDD 开发流程

## 标准流程

1. **确定板块**：用户明确提出要开发的板块。
2. **需求对话**：讨论目标、范围、用户流程、数据、权限、异常、验收标准和前后端契约。
3. **沉淀规格**：使用 `templates/module-spec.md` 创建 `specs/<module>.md`，状态先记 `Draft`。
4. **确认与转 Goal**：需求确认后把规格状态改为 `Approved`，将实现拆成可验证的 Goal。
5. **契约先行**：先确定 API 请求、响应、错误和前端数据模型，再并行实现两端。
6. **实现与联调**：按小功能推进，前端与后端完成真实联调；跨模块依赖保持显式。
7. **验证**：运行相关测试、静态检查、构建和端到端检查。
8. **文档与提交**：更新规范、`changelog.md`、`ai_resp.md`，完成一个可回滚的 commit。

## 需求变更

- 未实现前：直接修订对应规格，并记录变更原因。
- 实现中：先评估对数据模型、API 契约、前端状态和测试的影响，再更新规格并实施。
- 已实现后：保留原决策上下文，通过规格修订和 changelog 记录行为变化，不静默覆盖历史。

## 完成定义

一个小功能只有同时满足以下条件才算完成：

- 对应需求或规格条目已明确。
- 相关代码已实现并保持模块边界。
- 自动化测试或可复现验证通过。
- 前后端契约在真实开发环境中可用。
- 文档、变更记录与对话记录已更新。
- 形成独立 Git commit。

## 文档责任

- `docs/specs/`：回答“要做什么、为什么做、如何验收”。
- `docs/architecture/` 与 `docs/decisions/`：回答“系统如何组织、为什么这样选择”。
- `docs/standards/`：回答“代码必须遵守什么规则”。
- `docs/changelog.md`：回答“每次修改了什么”。
- `docs/ai_resp.md`：回答“需求是如何通过对话形成的”。
